# 引き継ぎ資料: QEMU ゲスト向け独自仮想デバイス開発

作成日: 2026-07-24
作成経緯: Cowork セッションでの設計検討の成果を Claude Code セッションへ引き継ぐためのまとめ。
本セッションではコード・リポジトリは未作成。成果物は本資料のみ。

## 1. プロジェクト概要

- 目的: Linux ゲストに対し、独自仮想デバイス経由でホスト側機能（例: 簡易自作レンダラ）を接続する。
- 副目的: 学習（デバイスドライバ開発、ホスト・ゲスト間通信の仕組みの理解）。目的の約半分を占める。
- 制約・方針:
  - QEMU 本体の改変は可能な限り回避する（無改変で成立する方式を優先）。
  - 実在ハードウェアの模倣はしない。他者の成果物（NDA 下の仕様、他社実装コード）の混入を避ける。
  - ゲスト OS は Linux 前提。

## 2. 検討した方式と採否

| # | 方式 | QEMU改変 | 評価 |
|---|------|----------|------|
| 1 | virtio-vsock / virtio-serial | 不要 | 採用（Phase 1） |
| 2 | ivshmem-plain / ivshmem-doorbell | 不要 | 採用（Phase 2, 3） |
| 3 | vhost-user（汎用 `vhost-user-device` フロントエンド利用） | 不要（要バージョン確認） | 将来の発展候補。virtio 学習に接続 |
| 4 | vfio-user / multiprocess QEMU | 不要（実験的） | 見送り。QEMU 側サポートの成熟度を要確認 |
| 5 | ツリー内カスタムデバイス（hw/misc/edu.c ベース） | 必要（フォーク維持） | 見送り。無改変方式で不足した場合の最終手段 |

選定理由: 1→2 の段階構成により「プロトコル設計 → ユーザ空間ドライバ → カーネルモジュール」と学習項目が積み上がり、かつ QEMU 無改変で完結するため。

## 3. 段階的実装計画

### Phase 1: vsock によるプロトコル確立

- ホスト: `-device vhost-vsock-pci,guest-cid=3` で起動。ホストデーモンが `AF_VSOCK` で listen。
- ゲスト: 標準ソケット API のみ。ドライバ開発なし。
- 成果物: レンダラのコマンドプロトコル定義（コマンド形式、フレーム受け渡し、フロー制御）、ホストデーモン、ゲスト側クライアント。
- 設計要点: 以降の Phase はこのプロトコルの輸送層を差し替えるだけにする（プロトコル定義と輸送層を分離した設計）。

### Phase 2: ivshmem-plain + UIO（ユーザ空間ドライバ）

- ホスト: `-object memory-backend-file,share=on,...` + `-device ivshmem-plain`。共有メモリがゲストに PCI BAR2 として見える。ホストプロセスは同一ファイルを mmap。
- ゲスト: `uio_pci_generic` を ivshmem（vendor:device = 1af4:1110）に bind し、ユーザ空間から BAR2 を mmap。カーネルコード不要。
- 通知: 割り込みなし。ポーリングで運用。
- 成果物: 共有メモリ上のコマンドリング＋フレームバッファのレイアウト定義、Phase 1 プロトコルの共有メモリ輸送層。

### Phase 3: ivshmem-doorbell + 自作カーネルモジュール（割り込み駆動）

- ホスト: `ivshmem-server` を起動し `-device ivshmem-doorbell,chardev=...` で接続。通知は eventfd。ホストプロセスも同サーバに接続して doorbell を送受信。
- ゲスト: 自作カーネルモジュールを実装。doorbell は既定で MSI-X のため `uio_pci_generic`（INTx のみ）では受けられない。MSI-X 対応の自作 UIO ドライバまたは通常の PCI ドライバが必要（学習の中核）。
- 成果物: ゲストカーネルモジュール、割り込み駆動版輸送層、Phase 2（ポーリング）とのレイテンシ・スループット比較。

## 4. 設計上の注意点（決定済み事項）

- 共有メモリ上のリング操作にはメモリバリアが必須。ホスト・ゲストは同一物理メモリを参照するが、コンパイラ・CPU のリオーダは通常の SMP と同様に発生する。
- リング設計は virtio の vring（avail/used index + barrier）を参考にする。将来 vhost-user へ進む場合の学習にも接続する。
- ゲストカーネルモジュールのビルドは、ゲスト用カーネルヘッダを含む環境をコンテナに用意し、ホスト環境を汚さない。

## 6. リポジトリ構成案（未作成・提案段階）

配置先: `~/repos/<project_name>`（プロジェクト名未定）

```
<project_name>/
├── proto/          # プロトコル定義（共有ヘッダ）。輸送層非依存
├── host/           # ホストデーモン（レンダラ本体を含むか分離するかは要検討）
├── guest/
│   ├── user/       # Phase 1-2: vsock クライアント / UIO ユーザ空間ドライバ
│   └── kmod/       # Phase 3: カーネルモジュール
├── scripts/        # QEMU 起動スクリプト、ゲストイメージ準備
├── containers/     # カーネルモジュールビルド用等のコンテナ定義
└── .tmp/           # gitignore 対象の作業ディレクトリ
```

## 7. 次のアクション（code session での最初の作業候補）

1. プロジェクト名の決定と `~/repos/<project_name>` でのリポジトリ初期化（git 管理、Conventional Commits）。
2. ゲスト環境の準備方針の決定: ディストリ選定、イメージ作成方法（cloud image + cloud-init 等）、QEMU 起動スクリプト整備。
3. Phase 1 のプロトコル v0 設計: レンダラのコマンドセット最小定義。
4. テスト戦略の具体化: プロトコル層のユニットテスト、ホスト・ゲスト結合テストの自動化方法（Phase 1 は vsock ループバックや CI 上の QEMU 起動で可能か検討）。

## 9. 利用者の開発方針（本プロジェクトへの適用事項）

- 依存パッケージは最小限とし、バージョンを SHA 等で固定。外部ツールは信頼できるコンテナ内で実行。
- 書き捨てスクリプトを避け、再現性・構成の整理・ドキュメント化を重視。
- テンポラリファイルはリポジトリ内の gitignore されたディレクトリで扱う。
- 機能追加は branch または worktree で実施。
